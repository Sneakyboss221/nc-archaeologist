2 · Basics and the problem 3 MIN · EXPLORER PAGE

"Let me quickly set the context.

A CNC milling machine is controlled by a program written in G-code, the ISO 6983 language. Each line is a command. For example, G01 X10 Y5 F300 means: cut in a straight line to X 10, Y 5, at 300 millimetres per minute. G00 is a fast move, G02 and G03 are arcs, G83 is a peck-drilling cycle.

In CIM, information is supposed to flow from CAD to process planning to CAM to the CNC machine. But in real factories that chain breaks. CAD systems get replaced, suppliers change, programmers retire. What survives on the shop floor is only the last link: the G-code. A shop can have thousands of programs named like O1234, and nobody knows what each one makes."

Point at the stats bar at the top: 600 programs in archive.

"This archive, for example, has 600 programs with no drawings and no labels.

That blocks three things CIM is supposed to give us:

One, reuse: when a new order comes in, finding out we already made a similar part, so we adapt a proven program instead of programming from scratch.

Two, Group Technology: grouping parts into families for machine cells and standard tooling, which is Module 6 of our syllabus.

And three, digital transformation: turning an unreadable archive into searchable data.

The obvious idea, comparing the program text, doesn't work. The same part can be written in millimetres or inches, absolute or incremental, with arcs or hundreds of tiny lines, clamped at any angle on the table, for a Fanuc or a Haas controller. Two programs for the same part can share almost no text."

3 · The idea and why it's novel 2 MIN

"So my idea is to treat each program as an executable description of geometry. Instead of reading the text, the system runs the program in a simulation, rebuilds the part that would come out of the machine, and then compares programs by what they make, not how they're written.

On novelty: rebuilding geometry from G-code has been studied, but only for 3D printing, for example Tsoutsos and colleagues in 2017, and Kiński and Sobieski in 2020. In printing, the toolpath is the part. In milling it's the opposite: the part is what's left after a rotating cutter removes material, so you have to simulate the cutter itself.

And Group Technology classification, like the Opitz code or production flow analysis, has always needed a CAD model, a drawing, or route sheets. To the best of my knowledge, this is the first approach that forms Group Technology part families directly from CNC programs.

It touches almost every module of the course: CNC and part programming, real-time CAM simulation, CAPP, Group Technology, and Big Data in manufacturing. Let me show you."

5 · How it works 3 MIN · HOW IT WORKS PAGE

Click How it works in the top menu. Scroll slowly as you talk; the right-hand boxes show live values for the flange you just ran.

"Here's the full method in six steps, with live numbers from that program.

Step 1, parsing. A modal state machine following ISO 6983. It keeps track of units, absolute or incremental mode, the active tool and the motion mode. It turns arcs into short straight segments and expands drilling cycles. It also executes parametric programs: variables, expressions, loops, subroutines and polar coordinates. Anything it can't run faithfully, like cutter compensation, gives a warning instead of a guess.

Step 2, cutter sizes. If the program states a tool's size in a comment, it uses that. If not, it finds the zig-zag pattern and measures the gap between passes, the step-over, which is usually about half the cutter diameter.

Step 3 is the simulation you just watched.

Step 4, the process sheet.

Step 5, features: the rebuilt part is sliced at each floor depth and each region is classified by shape, keeping features nested inside other features.

Step 6, the fingerprint: 75 numbers describing what the part is. These include shape statistics like Hu moments, which don't change when the part is rotated or moved, plus feature counts and the operation mix. Programs with similar fingerprints are grouped into families using Ward clustering, and a second method, HDBSCAN, flags unusual programs."

9 · Limitations and closing 1 MIN

"To be clear about the limits:

The main benchmark is synthetic, because no labelled dataset exists. The real LinuxCNC programs show it works on real files, but they don't have family labels, so the next step is validating on a real shop's archive.

It handles 3-axis parts; 5-axis and undercuts would need a tri-dexel model.

And when a program never states its tool sizes, accuracy drops, which is why it always flags it.

For future work: exporting the recognised features to STEP-NC, ISO 14649, so legacy parts can re-enter a modern CAD-CAPP-CAM chain, and linking the families to cell formation.

In summary: a legacy CNC program contains enough information to recover its part, its process plan and its family. By comparing programs on what they make rather than how they're written, it works across controllers and set-ups, where text comparison fails.

Thank you, sir. I'm happy to take any questions, or show any part in more detail."

10 · Answers to likely questions

Answer in one or two sentences, then stop. If he wants more, he'll ask.

Is the data real or fake?

"The main benchmark is synthetic, deliberately, because no public dataset of CNC programs with family labels exists, and synthetic data gives exact ground truth. I made it hard on purpose with four dialects, random rotation and missing tool comments, and I tuned on one set and tested once on another. I also ran 15 real, unmodified programs from the LinuxCNC project. For example, its polar-coordinate file should drill 26 holes and we found 26; a 3-inch bolt circle was measured as 76 millimetres."

Did you build this yourself?

Say what's true. A safe, honest version: "I designed the approach and the experiments, and I built it in Python using standard libraries like NumPy and scikit-learn, with AI coding assistance during development. I can walk you through any part of the code or method."

Being open about tools is far safer than being caught out, and the follow-up questions test understanding, not typing.

Why not just compare the G-code text?

"Because the same part can be written in completely different ways. In my results, text clustering scored 0.07 for families but 0.61 for writing style. It learns the dialect, not the part."

Why do you need to simulate? Can't you read the coordinates?

"The coordinates are the centre of a round cutter, not the part. The part is what's left after a cutter of a certain diameter and shape sweeps along that path, so you have to simulate the cutter to know what was removed."

What is a dexel / height map?

"The block is a grid of small columns, 0.25 mm wide, each storing its height. Each cutting move lowers the columns under the cutter to the cutter's tip plus its shape. It's 2.5D: one height per point, which is enough for 3-axis parts."

How do you find the tool size if it isn't written?

"From the zig-zag pattern: at least three parallel back-and-forth passes. The gap between them is the step-over, usually about half the cutter diameter. It covers 55 percent of tools in comment-free programs, 82 percent of those within one standard size. Drills can't be inferred, so a default is used and flagged."

What is the fingerprint? Why Hu moments?

"75 numbers: 46 describe shape, such as the depth distribution, seven Hu moments, a radial profile and feature counts, and 29 describe the process, such as the share of time per operation and the number of tools. Hu moments are shape descriptors that stay the same under rotation, translation and scale, so a part clamped at any angle gets the same fingerprint."

What does ARI 0.80 mean?

"Adjusted Rand Index: how well the discovered groups match the true families. 1 is perfect, 0 is random. 0.80 is strong; text comparison got 0.07."

How are the families formed?

"Ward hierarchical clustering, which repeatedly merges the two groups that add the least spread. When the number of families isn't known, the silhouette score picks it: it chose 9, and the true number is 8. HDBSCAN is also used to flag programs that don't fit anywhere."

What about cutter compensation, G41 / G42?

"With compensation the program describes the part edge and the controller offsets by the tool radius, which isn't in the file. So it's flagged as approximate rather than guessed."

Can it handle macros or parametric programs?

"Yes. It executes variables, expressions, loops, if/else and subroutines, both LinuxCNC style and Fanuc Macro B, plus polar coordinates. The real 3D carving is written entirely with variables. Only subroutines stored in other files can't be executed, and those are flagged."

What about 5-axis or lathe programs?

"5-axis isn't supported: the height map can't represent undercuts; that's future work with a tri-dexel model. Lathe programs are detected and flagged as 'not milling'." Show it: Run a sample → lathe program.

How would a factory actually use this?

"Run it once over the whole program archive. Then you can search 'have we made this before?' when quoting, use the families to plan cells and standardise tooling, and use the recovered parts and process sheets as documentation for legacy parts."

Why not use AI or an LLM?

"LLMs can generate G-code but don't reliably understand its geometry. Even the GLLM paper notes G-code has no semantic description of shape. This approach is physical and deterministic: it simulates the cutter, so every result is explainable and checkable."

How does this connect to the syllabus?

"CNC and part programming, Modules 2 and 3. Real-time CAM simulation, Module 4. CAPP and STEP, Module 5. Group Technology and FMS, Module 6. Big Data and digital transformation, Module 7."

What was the hardest part?

"Knowing where the raw block was, because G-code never states the stock size. I estimate it from the facing pass, which usually overruns the block by about one cutter radius. Another was real files: they used variables and loops that my test data didn't have, so I extended the interpreter to execute them."

How fast is it? What tools did you use?

"About 1.7 seconds per program on a laptop, run in parallel. Python with NumPy, SciPy, scikit-image and scikit-learn; a FastAPI server; the dashboard uses Three.js for 3D and Plotly for charts; the paper is LaTeX in IEEE format."

How did you generate the 1,200 test programs?

"With a generator I wrote in three parts. First, 8 parametric part families (bolt plate, pocket housing, slotted bracket, flange, stepped block, tray, keyway bar, boss) with random dimensions, hole counts and depths. Second, a mini CAM system that turns each part into toolpaths: zig-zag or spiral pocketing, peck drilling, slots, profiles. Third, four post-processors that write the same toolpath as Fanuc, Haas, comment-free, or inch-incremental G-code. Each part is also rotated and offset randomly on the table. The true family and exact designed geometry are saved separately and used only for scoring."

What would you do next?

"Validate on a labelled archive from a real shop, resolve cutter compensation from tool tables, extend to 5-axis, and export STEP-NC features."

11 · Under the hood IF HE SAYS "EXPLAIN EXACTLY WHAT HAPPENS"

Open the How it works page first, then go step by step. Stop after each step and ask "Shall I go deeper on this one?". He'll pick what interests him.

Input

"The input is one plain text file, a CNC program in G-code, ISO 6983: .nc, .ngc, .tap or .txt. That's all. No CAD model, no drawing, no stock size, no tool table. Each line is a block of words, a letter and a number, like G01 X25 Y10 F300. The output is the rebuilt part, the process sheet, the recognised features, a 75-number fingerprint and a part family."

Step 1: pre-processing, subprograms and macros

"Before interpreting, the program is flattened. Fanuc subprograms, M98 P2100 L4 with an O2100 … M99 body, are pasted in, four times in that case.

Parametric programs go through a macro interpreter. It has a tokenizer and a recursive-descent expression parser with operator precedence: logical operators lowest, then comparisons, then plus and minus, then multiply, divide and MOD, then power. It supports functions like SIN, COS, ATAN and SQRT in degrees. Parameters are stored in a table, numbered like #1 or named like #<scale>.

For control flow, a pre-scan builds a jump table matching every if/else/endif, while, repeat and sub/endsub. It then executes with a program counter, and a call stack saves subroutine arguments. Fanuc WHILE … DO / END works the same way. A step limit stops infinite loops. The output is plain G-code with every expression replaced by its number."

Step 2: the interpreter, a state machine

"The interpreter is a modal state machine, like a real CNC controller. G-code is modal: G1 stays active until another motion code, so a line with only X35 still means 'cut to X35'.

It tracks the motion mode, units (G20 inches are multiplied by 25.4), absolute or incremental mode, feed, spindle, the current tool, the drilling-cycle words Z, R and Q, and the retract plane. For each line it regex-tokenises the words, updates the modes, computes the target position (absolute, incremental, or polar with x = r cos a, y = r sin a), and emits a segment: start point, end point, rapid or cutting, tool, feed, spindle and the source line number.

For arcs, the centre comes from the I and J offsets, or from the R radius using chord geometry: the centre sits h = √(r² − (d/2)²) from the chord midpoint. The arc is cut into straight chords with an angle step of 2·acos(1 − tol/r), with a tolerance of 0.05 mm, which guarantees no chord deviates more than 0.05 mm from the true arc.

Drilling cycles like G83 are expanded into: rapid to the hole at the start height, rapid to R, feed to Z, retract. The peck count, ceil(depth / Q) − 1, goes into the cycle time. Anything it can't execute faithfully goes into a warnings list."

Step 3: cutter sizes

"Tool sizes come from comments when present: a regex reads the number, the diameter (with inches converted) and the type, flat, ball, drill or face. If a tool's sideways travel is under 5 percent of its vertical travel, it only plunges, so it's a drill.

When the size isn't written, I use what I call raster-run inference. Walking the moves at one depth, a pass is a move longer than 4 mm, a link is a short move between passes, and the next pass must run in the opposite direction (direction dot product below −0.9998). Three or more such passes make a zig-zag run. The perpendicular gap between passes is the step-over, and the diameter is the step-over divided by 0.5, snapped to the nearest standard cutter: 6, 8, 10, 12, 16 mm and so on."

Step 4: material-removal simulation

"The stock is a 2.5D dexel or height map: a NumPy 2D array with one height per 0.25 mm cell, covering all cutting moves plus the cutter radius plus a 2 mm margin. The stock top is Z = 0, the standard convention.

For every cutting move: new height = minimum of old height and tool tip height plus tool profile at distance r. The profile is zero for a flat end mill, R − √(R² − r²) for a ball end, and r / tan 59° for a 118° drill point.

For flat cutters it's exact, in closed form, with no sampling. Each cell is projected onto the move, giving a position t and a sideways distance p. The cutter covers that cell for t in an interval of half-width √(R² − p²) / L. Since height changes linearly along the move, the lowest point is at one end of that interval. This is vectorised with NumPy over a small window around each move. Ball and drill tools are sampled every 0.75 cell. For each tool it also stores which cells it removed and the volume: the sum of height change times cell area. It takes about one to two seconds per program."

Step 5: process sheet

"The program is split at each tool change and each block goes through a decision tree on what it removed:

  • plunges only → drilling
  • at most 1.6 mm deep over more than 45% of the area → facing
  • encloses an uncut island bigger than itself → profiling, that is, cutting the outline
  • runs past the stock edge → step milling
  • encloses a small island → island pocket
  • long, with width under 1.6 times the cutter → slotting
  • round → bore
  • otherwise → pocketing

Cycle time is the sum of length over feed, plus rapids at 10 metres per minute, 8 seconds per tool change and 1 second per peck. The stock edge is estimated from the facing toolpath, because facing passes overrun the block by about one cutter radius."

Step 6: feature recognition

"I compute the depth image, then find the floor depths: only flat cells, with slope under 0.05, so sloped drill cones don't create false levels. A 0.5 mm histogram gives the floor levels, and the depth map is sliced between them. At each level: morphological closing and opening to clean the grid edges, then connected-component labelling with SciPy. A region's parent is the region it sits inside one level up, which gives nesting.

For each region I measure circularity, 4πA / P²; the principal axes from PCA of its pixel coordinates, which give aspect, length and width; the fill ratio, area over length times width, which is 0.785 for a circle and about 1 for a square and so separates round from square pockets; and the enclosed island area. Then it's classified: hole if round and up to 14 mm, slot if long and narrow, step if open to the edge, and so on. A bolt circle needs the holes at the same distance from their centre within 5 percent and evenly spaced within 10 percent, because rectangle corners are also on a circle."

Step 7: fingerprint

"First I remove facing, the outer profile ring and anything outside the stock, because those depend on the raw blank, not the design. Then:

46 geometry numbers: a 12-bin depth histogram relative to the deepest cut; the 7 Hu moment invariants, log-scaled, which don't change with rotation, translation or scale; a 12-bin radial depth profile around the depth-weighted centre, normalised by the radius of gyration; 7 feature counts; and 8 shape terms like elongation, hole size and the bolt-circle flag.

29 process numbers: for 9 operation types, the share of time, whether it's present, and how many, plus the number of tools and tool changes.

Every number is z-scored, and each block is weighted 0.5 divided by the square root of its size so the larger block doesn't dominate."

Step 8: families, search, new uploads

"Ward agglomerative clustering repeatedly merges the two groups whose merger increases within-group variance the least. The number of families comes from the silhouette score over 4 to 12; it chose 9, and the truth is 8. HDBSCAN, a density-based method, finds families by itself and flags outliers.

'Find similar' uses cosine similarity between fingerprints. The map is t-SNE, a 2D projection for display only. A new upload gets the same fingerprint and scaling and joins the nearest family centre; if nothing is similar enough, it's flagged as a new part type."

Architecture and technologies

"It's a Python back end and a browser front end.

The analysis uses NumPy for the arrays and the simulation, SciPy for labelling and morphology, scikit-image for region properties and Hu moments, scikit-learn for scaling, Ward, HDBSCAN and t-SNE, and trimesh for STL export.

FastAPI with Uvicorn serves REST endpoints: upload and identify, program details, similar programs, compare, results. The 600-program archive is processed in parallel, one process per CPU core, and cached as JSON.

The height map is sent to the browser compactly as 16-bit integers. Three.js builds the 3D mesh from it, and the machining animation re-runs the cutter stamping in JavaScript, ending exactly on the server's result. Plotly draws the map and charts.

There are 22 pytest tests, and the paper is LaTeX in the IEEE template, with every number generated from the results file."

If he says "trace one line for me"

"Take G83 X25 Y0 Z-15 R2 Q3. The parser expands it into three segments: rapid down to Z 2, feed down to Z −15, rapid back up. The simulator lowers every cell within the drill radius around X 25 Y 0 to −15 plus the cone shape. Feature recognition finds a small, round connected region with circularity above 0.75 and diameter under 14 mm, so it's a hole. If the other holes sit at equal distance and even spacing around a centre, it reports a bolt circle with its diameter."
